Una nueva petición

Hasta ahora los datos estaban en el script. Con un formulario, los aporta el usuario.

Recuerda 2.1: al enviarlo, el navegador hace una nueva petición HTTP que lleva los datos; el servidor la procesa y responde con una nueva página.


<form action="RA3_altaCiclo.php" method="post">
  <input name="codCiclo">
  <input name="nombre">
  <button type="submit">Dar de alta</button>
</form>
action: a qué URL se envía. method: get o post. name: el nombre con el que llega el campo; sin name, no se envía.

Regla práctica: si solo lee, GET; si cambia algo, POST. En ambos casos, texto plano (para ocultar, HTTPS).

$_GET, $_POST, $_SERVER

Las superglobales de 2.4, ahora de verdad: arrays que PHP rellena en cada petición.


<?php
  $ciclo = $_GET['ciclo'] ?? '';   // lo escrito en <input name="ciclo">
?>

$_SERVER['REQUEST_METHOD']: 'GET' o 'POST'.

Al leerlos, tres cosas

  1. Un campo puede no llegar. Usamos siempre ?? (3.1): sin él, warning Undefined array key.
  2. Todo llega como string. Aunque sea type="number", recibes '2000', no 2000.
  3. Casillas y []. Sin marcar, no se envía; con name="modulos[]", llega como array.

Existe también $_REQUEST (mezcla GET+POST+cookies): no lo usaremos, conviene saber de dónde viene cada dato.

Mostrar y procesar en el mismo script


<?php
  if ($_SERVER['REQUEST_METHOD'] === 'POST') {
      // se ha enviado el formulario: procesar $_POST
  }
  // en cualquier caso, mostrar la página
?>

El peligro: XSS

<?= ?> (3.2) escribe tal cual. Ahora los datos vienen del usuario, que puede escribir HTML:


<script>alert('XSS')</script>

Si la página hace <?= $ciclo ?>, el navegador ejecuta ese código. Y basta un enlace malicioso (los datos pueden ir en la URL).

Escapar: htmlspecialchars()

Convierte <, >, &, ", ' en entidades HTML, que el navegador muestra en vez de interpretar.


<?php
  function e(string $texto): string
  {
      return htmlspecialchars($texto);
  }
?>
<p>Resultados para: <?= e($ciclo) ?></p>

Desde PHP 8.1, escapa también comillas simples y trabaja en UTF-8: no hacen falta más argumentos.

Regla de este REA

Todo dato externo se escapa al mostrarlo,
con e().

Cuesta poco y cierra la puerta al XSS.

Puente al Bloque 4. Laravel tiene un helper e() igual, y {{ $ciclo }} de Blade lo llama automáticamente.

Validar en el servidor

Validar: comprobar que los datos cumplen las reglas antes de usarlos.

HTML5 valida (required, type, min, max...) y conviene usarlo, pero no es una defensa: se desactiva con F12, y cualquiera puede construir la petición a mano.

La que de verdad cuenta: la del servidor.

filter_var()

Devuelve el valor ya convertido si es válido, o false si no.


<?php
  filter_var('2000', FILTER_VALIDATE_INT);    // 2000 (int)
  filter_var('dos mil', FILTER_VALIDATE_INT); // false

  // con rango
  filter_var('3000', FILTER_VALIDATE_INT, ['options' => ['min_range' => 1000, 'max_range' => 2000]]);  // false

  filter_var('https://youtu.be/curriculo1', FILTER_VALIDATE_URL);  // válida
  filter_var('ana@example.com', FILTER_VALIDATE_EMAIL);           // válido
?>
Existe también filter_input(INPUT_POST, 'horas', FILTER_VALIDATE_INT). Aquí usaremos filter_var() sobre un array de datos, porque sirve para cualquier array y se puede probar con un test sin una petición real.

Una función de validación

Recibe los datos y devuelve un array de errores por campo (vacío = válido).


<?php
function validarCiclo(array $datos): array {
    $errores = [];
    $codCiclo = trim($datos['codCiclo'] ?? '');
    if ($codCiclo === '') {
        $errores['codCiclo'] = 'El código del ciclo es obligatorio.';
    } elseif (!ctype_upper($codCiclo) || strlen($codCiclo) > 5) {
        $errores['codCiclo'] = 'El código debe tener como máximo 5 letras mayúsculas.';
    }
    // ... nombre y grado, con la misma idea ...
    $horas = filter_var($datos['horas'] ?? '', FILTER_VALIDATE_INT, [
        'options' => ['min_range' => 1000, 'max_range' => 2000],
    ]);
    if ($horas === false) {
        $errores['horas'] = 'Las horas deben ser un número entero entre 1000 y 2000.';
    }
    return $errores;
}
?>

trim() quita espacios; ctype_upper() exige mayúsculas.

Mostrar errores y conservar lo escrito

La página vuelve a mostrar el formulario con los errores y, para no reescribirlo todo, rellena cada campo (escapado):


<input name="nombre" value="<?= e($datos['nombre'] ?? '') ?>">

¿Y después de validar?

Lo normal: guardar (Bloque 5) y redirigir con GET — el patrón POST/Redirect/GET, que evita duplicar el alta al pulsar F5.

Para un mensaje tras redirigir hace falta recordar algo entre peticiones (2.4): una sesión, que llega en el Bloque 4.

Por ahora, tras validar: mostrar el resultado en la misma respuesta.

Puente al Bloque 4. $request->validate([...]), old('nombre'), redirect()->with(...), y protección CSRF con @csrf.
