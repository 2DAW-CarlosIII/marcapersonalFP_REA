Tres ideas distintas

  • Identificación: el usuario dice quién es (escribe su email).
  • Autenticación: lo demuestra, con algo que solo él debería tener (su contraseña).
  • Autorización: la aplicación decide qué puede hacer (un docente ve todos los currículos; un alumno, el suyo).

Aquí, las dos primeras. La autorización, con los roles: en 4.4 y en el Bloque 7.

Todos acaban igual: en cada petición, la aplicación tiene que saber qué usuario la hace. Con formulario + sesión, ese dato vive en $_SESSION.

Las contraseñas no se guardan

Se guarda su hash

Una función que no se puede invertir. Para comprobar, se rehace el cálculo con la contraseña recibida y se compara.

Si alguien roba los usuarios, no tiene las contraseñas, que mucha gente repite en otras cuentas.

password_hash() y password_verify()


<?php
$hash = password_hash('ana-secreta', PASSWORD_DEFAULT);
// $2y$12$Wq3... (60 caracteres, distinto cada vez)

password_verify('ana-secreta', $hash);   // true
password_verify('otra-cosa', $hash);     // false
?>

Sal y lentitud, a propósito

  • Algoritmo pensado para contraseñas (bcrypt), lento a propósito: probar millones cuesta.
  • Una sal aleatoria, guardada dentro del propio hash: dos ejecuciones, dos hashes distintos.
  • password_verify() extrae la sal, rehace el cálculo y compara.

md5() o sha1() no sirven: rapidísimas y sin sal.

Cuidado con las comillas

Un hash empieza por $2y$. Entre comillas dobles, PHP lo toma por variables:


'password' => "$2y$12$Wq3...",   // ✗ PHP intenta sustituir $2y...
'password' => '$2y$12$Wq3...',   // ✓ comillas simples

Los hashes, siempre entre comillas simples.

La clase Autenticador


class Autenticador
{
    public function __construct(
        private readonly array $usuarios,
    ) {
    }

    public function autenticar(string $email, string $password): ?array
    {
        $usuario = $this->usuarios[$email] ?? null;
        if ($usuario === null || !password_verify($password, $usuario['password'])) {
            return null;
        }
        return [ /* email, firstName, lastName, rol: sin el hash */ ];
    }
}

El mismo patrón que ValidadorCurriculo (3.8).

El login, paso a paso

  1. Regenera el identificador: session_regenerate_id(true)
  2. Guarda el usuario en $_SESSION['usuario']
  3. Mensaje flash y 303 al área del usuario, como en 4.1

¿Por qué regenerar? Fijación de sesión

Un atacante consigue que tu navegador use un PHPSESSID que él conoce (un enlace preparado; PHP acepta por defecto identificadores del cliente).

Si al hacer login no cambia, el atacante ya está dentro de tu sesión autenticada.

Con session_regenerate_id(true): identificador nuevo, y el antiguo se borra (el true).

Si las credenciales fallan

  • El mismo mensaje si falla el email o la contraseña: Email o contraseña incorrectos. Así no se revela qué emails tienen cuenta.
  • El formulario conserva el email, nunca la contraseña.

Páginas privadas: exigirLogin()


function exigirLogin(): array
{
    $usuario = usuarioActual();   // $_SESSION['usuario'] ?? null
    if ($usuario === null) {
        header('Location: RA4_login.php');   // 302
        exit;
    }
    return $usuario;
}

Y iniciarSesion(): el session_start([...]) de 4.1, en una función.

Cerrar la sesión

  1. Vaciar $_SESSION
  2. Borrar la cookie PHPSESSID: setcookie() con fecha ya pasada y la misma ruta
  3. Destruir la sesión en el servidor: session_destroy()

Con un formulario POST, no con un enlace: un GET lo dispararía cualquier página ajena (una imagen basta), y SameSite=Lax no protege los GET.
