De recordar a saber quién

4.1

La aplicación recuerda a un navegador entre peticiones.

4.2

Sabe quién está detrás: un formulario de login y una sesión que lo recuerda.

Sin login, cualquiera da de alta un currículo a nombre de cualquiera.

Tres ideas distintas

  • Identificación: el usuario dice quién es (escribe su email).
  • Autenticación: lo demuestra, con algo que solo él debería tener (su contraseña).
  • Autorización: la aplicación decide qué puede hacer (un docente ve todos los currículos; un alumno, el suyo).

Aquí, las dos primeras. La autorización, con los roles: en 4.4 y en el Bloque 7.

Formas de autenticarse

  1. Formulario + sesión: credenciales una vez; luego, la cookie
  2. HTTP Basic: usuario y contraseña en cada petición
  3. Token: se obtiene una vez y viaja siempre (API)
  4. Proveedor externo: identifica Google; luego, nuestra sesión
  5. Segundo factor (2FA): un paso más al entrar
Un mecanismo por pulsación; el punto recorre lo que viaja en cada petición siguiente. Todos acaban igual: en cada petición, la aplicación tiene que saber qué usuario la hace. Con formulario + sesión, ese dato vive en $_SESSION. HTTP Basic: Base64 no es cifrado, cualquiera lo decodifica; solo tiene sentido con HTTPS. Proveedor externo y segundo factor quedan fuera del alcance del módulo.

Las contraseñas no se guardan

Se guarda su hash

Una función que no se puede invertir. Para comprobar, se rehace el cálculo con la contraseña recibida y se compara.

Si alguien roba los usuarios, no tiene las contraseñas, que mucha gente repite en otras cuentas.

password_hash() y password_verify()


<?php
$hash = password_hash('ana-secreta', PASSWORD_DEFAULT);
// $2y$12$Wq3... (60 caracteres, distinto cada vez)

password_verify('ana-secreta', $hash);   // true
password_verify('otra-cosa', $hash);     // false
?>

Sal y lentitud, a propósito

  • Algoritmo pensado para contraseñas (bcrypt), lento a propósito: probar millones cuesta.
  • Una sal aleatoria, guardada dentro del propio hash: dos ejecuciones, dos hashes distintos.
  • password_verify() extrae la sal, rehace el cálculo y compara.

md5() o sha1() no sirven: rapidísimas y sin sal.

Cuidado con las comillas

Un hash empieza por $2y$. Entre comillas dobles, PHP lo toma por variables:


'password' => "$2y$12$Wq3...",   // ✗ PHP intenta sustituir $2y...
'password' => '$2y$12$Wq3...',   // ✓ comillas simples

Los hashes, siempre entre comillas simples.

La clase Autenticador


class Autenticador
{
    public function __construct(
        private readonly array $usuarios,
    ) {
    }

    public function autenticar(string $email, string $password): ?array
    {
        $usuario = $this->usuarios[$email] ?? null;
        if ($usuario === null || !password_verify($password, $usuario['password'])) {
            return null;
        }
        return [ /* email, firstName, lastName, rol: sin el hash */ ];
    }
}

El mismo patrón que ValidadorCurriculo (3.8).

autenticar(), en ejecución

  1. usuarios() devuelve el array, con los hashes
  2. El constructor guarda el array en $this->usuarios
  3. La página llama a autenticar() con lo que llegó por POST
  4. Busca el email; si no está, ?? null
  5. password_verify() rehace el hash y compara
  6. Devuelve los datos de Ana, sin el hash
  7. Falle lo que falle, null: el mismo resultado
Una llamada por pulsación; el punto recorre la llamada o el valor devuelto del paso actual. La barra vertical sobre la línea de vida del objeto es su "activación": el tiempo que autenticar() está ejecutándose. Paso 4: el operador ?? evita el aviso de índice inexistente; con el || del if, si $usuario es null, password_verify() ni siquiera se evalúa (evaluación en cortocircuito). Paso 7: los dos fallos devuelven lo mismo, por eso la página puede mostrar un único mensaje y no revela qué emails existen. Lo que pasa después con el array devuelto (regenerar el id y guardarlo en $_SESSION) es la siguiente diapositiva.

El login, paso a paso

  1. Ana usará un id que el atacante conoce (fijación)
  2. Ana envía email y contraseña con esa cookie
  3. password_verify() compara con el hash
  4. session_regenerate_id(true): abc, borrada
  5. 303 con la cookie nueva (xyz)
  6. Ana entra: exigirLogin() la reconoce
  7. abc ya no existe: sin regenerar, entraría
Un paso por pulsación; el punto recorre la petición o la respuesta del paso actual. PHP acepta por defecto identificadores que le llegan del cliente; por eso la fijación es posible. El true de session_regenerate_id(true) es lo que borra la sesión antigua: sin él, abc seguiría existiendo (vacía).

Si las credenciales fallan

  • El mismo mensaje si falla el email o la contraseña: Email o contraseña incorrectos. Así no se revela qué emails tienen cuenta.
  • El formulario conserva el email, nunca la contraseña.

Páginas privadas: exigirLogin()


function exigirLogin(): array
{
    $usuario = usuarioActual();   // $_SESSION['usuario'] ?? null
    if ($usuario === null) {
        header('Location: RA4_login.php');   // 302
        exit;
    }
    return $usuario;
}

Y iniciarSesion(): el session_start([...]) de 4.1, en una función.

Cerrar la sesión

  1. Vaciar $_SESSION
  2. Borrar la cookie PHPSESSID: setcookie() con fecha ya pasada y la misma ruta
  3. Destruir la sesión en el servidor: session_destroy()

Con un formulario POST, no con un enlace: un GET lo dispararía cualquier página ajena (una imagen basta), y SameSite=Lax no protege los GET.
