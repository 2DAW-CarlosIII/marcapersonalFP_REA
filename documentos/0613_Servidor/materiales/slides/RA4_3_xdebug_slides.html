4.3. Depuración
con Xdebug

Mirar dentro del código mientras se ejecuta

marcapersonalFP v0, todavía en PHP plano

Xdebug ya quedó instalado y configurado en §7 de la preparación del entorno: aquí aprendemos a usarlo. Tecla S: vista del ponente. Tecla O: vista general.

Errores que no avisan

Hasta ahora

El mensaje de error de PHP (display_errors, 2.2) y los tests.

Pero…

Hay programas que se ejecutan sin quejarse y, simplemente, calculan mal.

Hay que ver qué valor tiene cada variable, por qué rama pasa, cuántas vueltas da: un depurador.

Depurar con trazas


<?php
var_dump($curriculos);   // tipo y valor, con detalle
print_r($cuenta);        // más legible para arrays
error_log('cuenta: ' . print_r($cuenta, true));   // al registro
?>
  • Hay que modificar el código, y acordarse de quitarlas.
  • Solo muestran lo que decidiste mirar antes de ejecutar.
  • En una página que redirige, ni se ven.

Un depurador permite…

  • Detener la ejecución en una línea: punto de ruptura (breakpoint)
  • Avanzar paso a paso
  • Ver todas las variables en cada momento, sin tocar el código

Cómo funciona Xdebug

  1. El editor (VS Code + PHP Debug) escucha en el puerto 9003.
  2. Llega una petición con un disparador (trigger).
  3. Xdebug, desde php-fpm, se conecta al editor: el servidor llama al editor, no al revés.
  4. El editor controla la ejecución: dónde parar, cuándo avanzar, qué mostrar.

Ya configurado (§7 del entorno)


xdebug.mode=debug
xdebug.start_with_request=trigger
xdebug.client_host="dockerhost"
xdebug.client_port=9003
  • debug: depuración paso a paso.
  • trigger: solo se depura la petición que lleva el disparador; las demás, normales.
  • dockerhost:9003: dónde está el editor, visto desde el contenedor.

El disparador: XDEBUG_TRIGGER

En la URL, para un GET:


http://localhost/RA4_resumen.php?XDEBUG_TRIGGER=1

Como cookie, para todas las peticiones (también los POST). Desde la consola de F12:


document.cookie = 'XDEBUG_TRIGGER=1; path=/';

Xdebug Helper (Chrome) lo hace con un botón, con la cookie XDEBUG_SESSION: el nombre antiguo, que Xdebug sigue aceptando.

VS Code: .vscode/launch.json


{
    "version": "0.2.0",
    "configurations": [{
        "name": "Xdebug (vanilla_php)",
        "type": "php",
        "request": "launch",
        "port": 9003,
        "pathMappings": {
            "/var/www/vanilla_php": "${workspaceFolder}"
        }
    }]
}

Extensión PHP Debug (xdebug.php-debug) y la carpeta vanilla_php abierta.

¿Por qué pathMappings?

Xdebug (contenedor)

/var/www/vanilla_php/public/RA4_resumen.php

VS Code (máquina virtual)

~/Documentos/laravel/vanilla_php/public/RA4_resumen.php

Sin la traducción, la conexión se establece pero el editor nunca se detiene en tus puntos de ruptura.

El depurador, en marcha

ContinuarF5Hasta el siguiente punto de ruptura
Por encimaF10La línea entera, aunque llame a funciones
Por dentroF11Entra en la función que llama
SalirMayús+F11Vuelve a quien llamó
DetenerMayús+F5Deja de escuchar

Se detiene antes de ejecutar la línea marcada.

Lo que puedes ver

  • Variables: las locales y las superglobales ($_POST, $_SESSION, $_COOKIE…)
  • Inspección (Watch): expresiones vigiladas, como $cuenta['DAW']
  • Pila de llamadas: qué función llamó a cuál
  • Consola de depuración: evalúa cualquier expresión con los valores del momento
  • Punto de ruptura condicional: solo si $codigo === 'DAW'

Si no se detiene

  1. ¿VS Code escucha? (barra inferior coloreada)
  2. ¿La petición lleva el disparador?
  3. ¿El punto de ruptura está en una línea que se ejecuta?
  4. ¿pathMappings coincide con tu carpeta?

Depurar también los tests

Xdebug también está en workspace. El disparador, como variable de entorno:


docker compose exec -e XDEBUG_TRIGGER=1 --workdir /var/www/vanilla_php \
  workspace vendor/bin/phpunit tests/RA4_3_XdebugTest.php

Con un punto de ruptura en el test o en src/, se detiene igual que con una página.

Un test

Ejercicios (1/2)

  1. ¿Está Xdebug activo? public/RA4_xdebug.php: "cargado" y modo debug.
  2. Prepara VS Code. PHP Debug, launch.json, un punto de ruptura y ?XDEBUG_TRIGGER=1: ¿se detiene?
  3. Un resumen que calcula mal. src/RA4_depuracion.php con sus errores y public/RA4_resumen.php.

Ejercicios (2/2)

  1. Encuentra los errores con el depurador, sin var_dump(): F10 vuelta a vuelta vigilando $cuenta; un punto condicional; evalúa intdiv($parte, $total) y $parte / $total. Corrige y explica.
  2. Depura un test con -e XDEBUG_TRIGGER=1: ¿qué muestra la pila de llamadas?
  3. Investiga. ¿Y si $total vale 0? DivisionByZeroError.

Puente al Bloque 5

  • Xdebug no sabe nada del framework: solo ve PHP. En Laravel se depura igual.
  • Todas las peticiones entran por public/index.php; pathMappings apuntará al proyecto Laravel.
  • Para trazas rápidas: dump() y dd() (dump and die).
