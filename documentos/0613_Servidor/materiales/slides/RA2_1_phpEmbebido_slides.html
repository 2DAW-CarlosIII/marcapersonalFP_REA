De la página estática a la dinámica

Estática

  • Fichero .html que el servidor entrega tal cual
  • Igual para todos los visitantes

Dinámica

  • El servidor ejecuta código en el momento de la petición
  • El HTML cambia según los datos, el usuario o el momento
Pregunta al grupo: ¿qué páginas que uséis a diario muestran algo distinto según quién sois o cuándo entráis?

Código embebido

  • Escribimos HTML normal…
  • …y donde necesitamos que "pase algo", insertamos fragmentos de código
  • El servidor los ejecuta antes de enviar la respuesta
  • El navegador nunca ve ese código: solo recibe el HTML resultante

El flujo en producción

Navegador y servidor en máquinas distintas: petición y respuesta viajan por Internet.

El flujo en nuestro entorno

Todo convive en la VM, pero la petición y la respuesta HTTP siguen siendo reales.

Insistir: al no haber red de por medio es fácil olvidar que sigue habiendo petición y respuesta HTTP. Solo cambia el "viaje": ocurre entre programas de la misma máquina, no entre dos máquinas.

Idea clave

El cliente recibe HTML.
El código se queda y se ejecuta en el servidor.

Y esto no cambia porque, en desarrollo, cliente y servidor compartan máquina.

Tecnologías asociadas

  • PHP Se embebe con <?php … ?>. El atajo <?= $x ?> equivale a echo. — el que usaremos: nació para embeberse en HTML
  • ASP / ASP.NET ASP clásico usa <% … %>. En ASP.NET, las vistas Razor mezclan HTML y C# con @. — Microsoft
  • JSP JavaServer Pages: <% … %> y <%= … %>; hoy se prefiere el lenguaje de expresiones ${…}. — plataforma Java
  • Python Sin "código embebido" nativo: se usan plantillas (Jinja2 en Flask, las de Django) con {{ … }} y {% … %}. — WSGI/ASGI con Django o Flask
  • JavaScript (Node.js) Con Express y motores de plantillas: EJS usa <% … %> (muy parecido a PHP); Handlebars, {{ … }}. — Express + EJS / Handlebars

Pasa el ratón por cada una para ver cómo embebe el código.

Misma idea (código que el servidor ejecuta para producir el marcado del cliente); cambian sintaxis y ecosistema. PHP por ser el más extendido en la web y la base sobre la que se construye Laravel. Enlaza con el ejercicio 4.

Las etiquetas <?php ?>

En un fichero .php, todo se envía al navegador tal cual, como HTML,
excepto lo que quede entre las etiquetas de PHP:


<?php
  // Esto es código PHP: el servidor lo ejecuta, el navegador no lo ve.
?>
<?php abre una zona de código PHP
?> cierra la zona y vuelve al modo HTML

HTML y PHP en el mismo documento


<!DOCTYPE html>
<html lang="es">
<head>
    <meta charset="UTF-8">
    <title>marcapersonalFP v0</title>
</head>
<body>
    <h1>Hola, marcapersonalFP</h1>
    <p>Esta página se ha generado el <?php echo date('d/m/Y H:i:s'); ?>.</p>
</body>
</html>

Todo el HTML se envía sin cambios; solo ese fragmento se ejecuta en el servidor y se sustituye por su resultado.

Primer clic: el documento completo. Segundo clic: la línea 9, la única que ejecuta el servidor. Si recargas la página, la hora cambia: eso es una página dinámica.

¿Qué recibe el navegador?

Lo que escribes · RA2_holaMundo.php


<p>Esta página se ha generado el <?php echo date('d/m/Y H:i:s'); ?>.</p>

↓ el servidor ejecuta el PHP y envía…

Lo que recibe el navegador · HTML


<p>Esta página se ha generado el 21/09/2026 09:30:12.</p>

Cada recarga produce otra hora: página dinámica.

¿Cerrar o no cerrar ?>?

Solo código PHP

Convención: omitir el ?> final.

Evita problemas con espacios en blanco accidentales. Lo veremos en las clases del proyecto.

HTML mezclado con PHP

Abrimos y cerramos cada fragmento.

Como en RA2_holaMundo.php.

Un espacio o salto de línea tras el ?> final se envía al navegador y puede provocar el clásico error "headers already sent" cuando más adelante se intenten enviar cabeceras.

Dos contenedores, dos trabajos

Un único entorno para todo el curso: la VM con Laradock (Docker + nginx + php-fpm).

nginx

La puerta HTTP (puerto 80).

Es a quien apunta el navegador.

php-fpm

El motor que ejecuta el PHP.

Habla FastCGI por el puerto 9000, no HTTP.

Necesitamos los dos levantados.

Si algún alumno no tiene la máquina virtual: primero "0. Instalación y preparación del entorno".

Levantar el entorno


# desde la carpeta laradock/
docker compose up -d nginx php-fpm

En Laradock nginx depende de php-fpm: un comando levanta ambos.


~/Documentos/laravel/
├── laradock/
└── vanilla_php/
    └── public/               ← raíz web de nginx
        └── RA2_holaMundo.php

En el contenedor, la raíz web es /var/www/vanilla_php/public.

Tu primer script

  1. Guarda el ejemplo HTML + PHP como vanilla_php/public/RA2_holaMundo.php
  2. Abre en el navegador http://localhost/RA2_holaMundo.php
Navega al fichero concreto. Con http://localhost/ a secas y sin index.php obtendrás un 404.
¿Puerto 80 ocupado? Cambia NGINX_HOST_HTTP_PORT en el .env de Laradock (p. ej. 8080) y usa http://localhost:8080/RA2_holaMundo.php.
Error muy típico: hacer doble clic en el .php (file://) y ver el código sin ejecutar. Debe abrirse siempre a través de http://localhost, que es lo que pasa por nginx y php-fpm.

Comprueba que el código vive en el servidor

  1. Con la página abierta: Ctrl+U ("Ver código fuente")
  2. No aparece ninguna etiqueta <?php ?>: solo el HTML final, con la fecha ya sustituida
  3. Compáralo con vanilla_php/public/RA2_holaMundo.php: ahí sí está el código

Esa es la prueba de que PHP se ejecutó en el servidor.

Lo esencial

  • El servidor ejecuta el PHP; el navegador solo recibe HTML
  • Todo lo que queda fuera de <?php ?> se envía tal cual
  • nginx atiende HTTP y php-fpm ejecuta el código; los scripts van en vanilla_php/public/
  • Ctrl+U nunca mostrará código PHP

Comprueba tu solución (opcional)
