¿Qué es un framework?

Librerías y convenciones que automatizan el trabajo, a cambio de seguir sus reglas.

  • Una sola puerta de entrada: public/index.php, y las rutas deciden quién atiende cada petición.
  • Cada cosa en su sitio: lógica en controladores y app/; HTML en vistas Blade (MVC, en 5.8).
  • Lo repetitivo, hecho: sesiones, CSRF, validación, autenticación, escape.
Retomar la definición de framework de la nota de 00 §11. Ahora ya sabemos qué trabajo automatiza.

Un repositorio por curso

  • Repositorio base, en la organización: 2DAW-CarlosIII/marcapersonalfp2627. En tu clon, el remoto upstream.
  • Tu fork, en tu cuenta: <tu-usuario>/marcapersonalfp2627. El remoto origin.
  • Tu clon local: ~/Documentos/laravel/marcapersonalfp, donde trabajas.

Subes tus ramas a tu fork y propones los cambios al base con un pull request.

El flujo de trabajo

1 fork, 2 clone, 3 rama del ejercicio, 4 push a tu fork, 5 pull request al base, 6 pull desde upstream, 7 siguiente rama.

Cómo nació el repositorio base

Una vez por curso, el profesorado. Sin PHP en la VM, Composer va en un contenedor de usar y tirar:


cd ~/Documentos/laravel
docker run -it --rm -v "$PWD:/usr/src/app" thecodingmachine/php:8.4-v4-slim-cli \
    composer create-project laravel/laravel:^13.0 marcapersonalfp

Después, git init y push a 2DAW-CarlosIII/marcapersonalfp2627.

El .gitignore deja fuera vendor/, .env y la base SQLite: tú los regeneras en el paso 4.

La imagen de thecodingmachine crea los ficheros a nombre del dueño de la carpeta, no de root. create-project ejecuta además los scripts post-create-project-cmd (ejercicio Investiga). Las migraciones fallan con "could not find driver": la imagen slim no trae pdo_sqlite. No importa, la base no se sube.

Pasos 1 y 2: fork y clon

Botón Fork en el repositorio base. Después, en la VM (allí están tus claves SSH):


cd ~/Documentos/laravel
git clone git@github.com:<tu-usuario>/marcapersonalfp2627.git marcapersonalfp
cd marcapersonalfp
git remote add upstream git@github.com:2DAW-CarlosIII/marcapersonalfp2627.git
git remote -v

La carpeta se llama marcapersonalfp todos los cursos.

Paso 3: un terminal dentro de workspace

Composer y Artisan necesitan PHP. Desde laradock:


docker compose up -d nginx php-fpm workspace
docker compose exec --user=laradock --workdir /var/www/marcapersonalfp workspace bash

Indicador: laradock@…:/var/www/marcapersonalfp$. Para salir, exit.

composer y php artisan, aquí. git y docker compose, en otro terminal de la VM.

¿Por qué --user=laradock?

Sin la opción: root

Los ficheros que crea son de root.

En vanilla_php no importaba: php-fpm solo leía.

Laravel escribe

php-fpm (www-data) escribe en la base SQLite, en storage/logs/ y en storage/framework/.

Si son de root: error 500.

laradock es tu usuario de la VM, y en php-fpm ese usuario es www-data.

Paso 4: dependencias y configuración


composer install
cp .env.example .env
php artisan key:generate
php artisan migrate
  1. vendor/, con las versiones de composer.lock.
  2. .env: la configuración de esta instalación. No se sube.
  3. APP_KEY: cifra las cookies y la sesión.
  4. Crea database.sqlite (responde que sí) y sus tablas.
Después, php artisan about debe mostrar Laravel 13 y PHP 8.4. El .env lleva secretos (APP_KEY); se sube su plantilla, .env.example.

Paso 5: el sitio de nginx


cd ~/Documentos/laravel/laradock/nginx/sites
cp laravel.conf.example marcapersonalfp.conf

En marcapersonalfp.conf:


server_name marcapersonalfp.test;
root /var/www/marcapersonalfp/public;
        

echo "127.0.0.1  marcapersonalfp.test" | sudo tee -a /etc/hosts
docker compose restart nginx        # desde laradock
root apunta a public/: .env, vendor/ y app/ quedan fuera del alcance de nginx.

Dos sitios conviven

Los tests de los Bloques 2 a 4 lo necesitan.

http://marcapersonalfp.test

marcapersonalfp.conf → Laravel

Página de bienvenida de Laravel.

nginx elige el sitio por el nombre que pide el navegador: server_name.

Paso 6: una rama por apartado


git switch -c RA5_1
git add .
git commit -m "Soluciona los ejercicios de 5.1"

git push origin main

En GitHub: pull request de tu rama hacia el main del repositorio base.

Los acepta el profesorado; más adelante, también compañeros con permisos.
