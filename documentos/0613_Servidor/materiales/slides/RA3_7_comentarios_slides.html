Para qué sirve un comentario

Texto que el intérprete ignora: no se ejecuta ni produce salida. Solo para quien lee el código.

Un buen comentario explica por qué,
no qué.

El "qué" ya lo dice el código; si no se entiende, mejor mejorar los nombres.

Mal y bien


<?php
  // Mal: repite lo que ya dice el código
  $anios++;   // suma 1 a $anios

  // Bien: explica una decisión que el código no cuenta
  // Solo los ciclos de Grado Superior dan acceso directo a la universidad.
  if ($grado === 'Superior') {
      // ...
  }
?>

Tres formas en PHP


<?php
  // Comentario de una línea: desde // hasta el final de la línea

  # También de una línea, al estilo de la consola (poco usado)

  /*
     Comentario de varias líneas:
     desde /* hasta el cierre.
  */

  $horas = 2000;   // también al final de una sentencia
?>

Cuidado con ?>

Un comentario de una línea (// o #) termina al final de la línea… o al encontrar ?>, lo que ocurra antes.

Lo que haya detrás de ?> ya no es PHP: se envía como HTML. Lo comprobarás en el ejercicio 2.

Los de varias líneas (/* */) no tienen este problema.

# no siempre es comentario

Desde PHP 8, #[ inicia un atributo: información que PHP sí lee, no un comentario.

Ya los has visto sin saberlo: PHPUnit usa #[DataProvider]. Lo investigarás al final.

Comentar código temporalmente

Útil al depurar (como en los ejercicios de 3.5), pero no dejes código comentado en la versión final: es ruido que nadie se atreve a borrar.

Si necesitas recuperar código antiguo, para eso está el historial de git.

Comentarios PHP frente a HTML


<?php
  // Comentario PHP: el servidor lo descarta
?>
<!-- Comentario HTML: el servidor lo envía tal cual -->

Recuerda 2.1: el navegador solo recibe el HTML resultante. Un comentario HTML no se ve, pero cualquiera puede leerlo con "Ver código fuente".

Consecuencia práctica

Notas internas —credenciales, rutas,
decisiones de negocio— van
siempre en comentarios PHP.

Nunca en comentarios HTML.

Docblocks

Un comentario de varias líneas que empieza por /**, justo antes de una función, clase, método o propiedad. Formato PHPDoc.


<?php
/**
 * Devuelve los currículos de un ciclo, reindexados desde 0.
 *
 * @param array<int, array{alumno: string, ciclo: string}> $curriculos
 * @param string $codCiclo Código del ciclo, por ejemplo 'DAW'.
 * @return array<int, array{alumno: string, ciclo: string}>
 */
function curriculosDeCiclo(array $curriculos, string $codCiclo): array
{ /* ... */ }
?>

Etiquetas PHPDoc

EtiquetaDocumenta
@param tipo $nombre …Un parámetro
@return tipo …El valor devuelto
@throws Clase …Un error que puede lanzar
@var tipoEl tipo de una propiedad o variable

¿Docblocks, con tipos declarados?

En 3.4: los tipos ya documentan por sí solos. Pero tienen un límite: array no dice qué contiene.

  • array<int, string>: indexado de strings
  • array{alumno: string, ciclo: string}: asociativo con esas claves (array shape)
  • array<int, array{...}>: una lista de esos registros

PHP no los comprueba… otros sí

Son comentarios: PHP no los evalúa al ejecutar. Pero los leen el editor, PHPStan, los generadores de documentación y los asistentes de IA.

Tipos declarados siempre que se pueda;
docblock cuando aporta algo que el tipo no puede expresar.

Un docblock que solo repite @param string $codCiclo es ruido, como los comentarios del principio.

Puente al Bloque 4: el código de Laravel está lleno de docblocks. En el Bloque 6, OpenAPI/Swagger lleva esta misma idea (describir formalmente qué recibe y qué devuelve) a los servicios web.

Lo esencial

  • //, # (una línea) y /* */ (varias); ojo con ?>
  • Comentario PHP: se queda en el servidor. Comentario HTML: llega al navegador
  • Explica el por qué, no el qué; sin código comentado en la versión final
  • Docblock: cuando aporta algo que el tipo declarado no puede decir
