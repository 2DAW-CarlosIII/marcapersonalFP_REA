5.7. Middleware y Breeze

Control de usuarios

De exigirLogin() en cada página a una capa alrededor de todas

Cuarta fila del plan del bloque: el login de 4.2, ahora con middleware y con Breeze como caja negra. Tecla S: vista del ponente. Tecla O: vista general.

De exigirLogin() al middleware


$usuario = exigirLogin();    // al principio de cada página privada de v0 (4.2)
  • Dependía de que cada página se acordara. Una que lo olvidara quedaba abierta, y nada avisaba.
  • Laravel pone la comprobación alrededor de las páginas: en un middleware.
  • Las rutas declaran qué las protege; route:list -v lo muestra de un vistazo.

Qué es un middleware

Las capas que la petición cruza antes del controlador, y la respuesta de vuelta (5.2).


public function handle(Request $request, Closure $next): Response
{
    // ...
    return $next($request);
}
  • $next: "lo que viene después", el siguiente middleware y, al final, el controlador.
  • Ya los usábamos: la sesión, el token CSRF (5.6), $errors en las vistas.

Tres decisiones

Dejarla pasarreturn $next($request);
Desviarla a otra páginareturn redirect()->route('login');
Cortarla con un errorabort(403);

Las capas de middleware

  1. Con sesión: cada capa actúa antes de $next() y la petición llega al controlador
  2. La respuesta vuelve por las capas (después de $next()): StartSession guarda la sesión
  3. Sin sesión: auth no encuentra usuario…
  4. …y responde con una redirección a /login: el controlador no se ejecuta
Las dos primeras capas son del grupo web y se aplican a todas las rutas; auth solo a las rutas que lo declaran. En un GET, PreventRequestForgery no tiene token que comprobar: solo actúa en POST, PUT, PATCH y DELETE. Paso 4: es lo que hacía exigirLogin() en 4.2, pero fuera de la página.

¿Antes o después de $next?


public function handle(Request $request, Closure $next): Response
{
    // Antes: se puede examinar la petición y decidir si continúa.

    $response = $next($request);

    // Después: se puede examinar o modificar la respuesta.

    return $response;
}

exigirLogin() actuaba antes. StartSession, en los dos: abre la sesión y la guarda.

Un middleware propio


php artisan make:middleware CabeceraCentro
        

class CabeceraCentro
{
    public function handle(Request $request, Closure $next): Response
    {
        $response = $next($request);

        $response->headers->set('X-Centro', config('marcapersonalfp.centro'));

        return $response;
    }
}

Actúa después: una cabecera HTTP con el centro de 5.2.

Dónde se aplica

  1. A todas las peticiones (global), en bootstrap/app.php.
  2. A un grupo: las rutas de web.php, y lo que incluye, son del grupo web.

// bootstrap/app.php
->withMiddleware(function (Middleware $middleware): void {
    $middleware->web(append: [CabeceraCentro::class]);
})
  1. A rutas concretas: ->middleware(CabeceraCentro::class), en una ruta o un grupo.

Proteger rutas con auth


Route::controller(ProyectosController::class)->prefix('proyectos')->name('proyectos.')
->group(function () {
    // Públicas
    Route::get('/', 'index')->name('index');
    Route::get('show/{id}', 'show')->whereNumber('id')->name('show');

    // Solo para usuarios identificados
    Route::middleware('auth')->group(function () {
        Route::get('create', 'create')->name('create');
        Route::post('/', 'store')->name('store');
        Route::get('edit/{id}', 'edit')->whereNumber('id')->name('edit');
        Route::put('edit/{id}', 'update')->whereNumber('id')->name('update');
    });
});

Sin sesión, auth redirige a /login: exigirLogin(), declarado en un solo sitio.

El login, con Breeze

  1. Sin sesión, auth guarda a dónde ibas y redirige a /login
  2. GET /login: el formulario, en una ruta con guest
  3. Auth::attempt() comprueba el hash; regenerate() cambia el id de la sesión
  4. redirect()->intended(): de vuelta a la página que pedías
  5. Ahora auth deja pasar: el formulario de edición
Es el login de 4.2 (diapositiva "El login, paso a paso"), ahora sin escribir nada: Auth::attempt hace el password_verify, regenerate hace el session_regenerate_id. Lo nuevo frente a v0: url.intended. En v0, tras el login, siempre íbamos a la misma página. Paso 3: la respuesta del POST es la redirección del paso 4, con la cookie del id nuevo.

Puente

En v0

Cada página privada debía llamar a exigirLogin(); el login, el hash y la regeneración, a mano.

En Laravel

auth protege grupos de rutas desde un sitio, y Breeze trae registro, recuperación y límite de intentos.

Esto que hicimos a mano, el framework lo automatiza así.
