El objeto Request

Ni $_GET ni $_POST: toda la petición, en un objeto. Se declara como parámetro:


use Illuminate\Http\Request;

public function store(Request $request)
{
    $nombre = $request->input('nombre');
    // ...
}
  • Nadie lo pasa: Laravel ve el tipo y entrega la petición. Inyección de dependencias (5.8).
  • Los parámetros de la ruta, después: update(Request $request, int $id).

Todos son métodos de $request.

Formularios: la dirección de envío


// routes/proyectos.php, dentro del grupo de 5.5
Route::post('/', 'store')->name('store');
Route::put('edit/{id}', 'update')->whereNumber('id')->name('update');
  • POST /proyectos → store: guarda uno nuevo.
  • PUT /proyectos/edit/{id} → update: guarda los cambios.
  • En el formulario, con route(): action="{{ route('proyectos.store') }}"

El token CSRF: @csrf


<form action="{{ route('proyectos.store') }}" method="POST">
    @csrf
    ...
</form>
  • Un campo oculto con un token guardado en la sesión.
  • Un middleware lo comprueba en cada POST, PUT o DELETE. Una página ajena no lo conoce.
  • Sin @csrf: error 419 (Page Expired). En 4.1 solo teníamos SameSite.

PUT, PATCH y DELETE

HTML solo envía GET y POST (5.3). El resto, por POST con @method:


<form action="{{ route('proyectos.update', $id) }}" method="POST">
    @csrf
    @method('PUT')
    ...
</form>

Añade un campo oculto _method: Laravel lo trata como PUT y llega a Route::put().

Validación: validate()


public function store(Request $request)
{
    $datos = $request->validate([
        'docente_id' => ['required', 'integer', 'min:1'],
        'nombre' => ['required', 'string', 'max:100'],
        'dominio' => ['required', 'alpha_dash', 'max:60'],
        'fecha_inicio' => ['required', 'date'],
        'fecha_fin' => ['nullable', 'date', 'after_or_equal:fecha_inicio'],
        'calificacion' => ['nullable', 'numeric', 'between:0,10'],
    ]);

    // Aquí, $datos solo contiene los campos validados.
}

Las reglas

requiredQue llegue y no esté vacío
nullablePuede estar vacío; si tiene valor, se comprueba el resto
string, integer,
numeric, date		El tipo de dato
min:1, max:100,
between:0,10		Mínimo o máximo; en los textos, la longitud
alpha_dashLetras, números, guiones y guiones bajos
after_or_equal:fecha_inicioIgual o posterior a otra fecha

¿Y si algo no es válido?

validate() no deja continuar:

  1. guarda en la sesión los errores de cada campo;
  2. guarda lo que había escrito el usuario (old input);
  3. redirige de vuelta al formulario.

Si son válidos, devuelve solo los campos validados: un campo añadido con F12 (el truco de 4.4) se queda fuera.

El viaje de un formulario

  1. GET: el formulario, con su token @csrf
  2. POST no válido: errores y lo escrito, a la sesión; vuelta atrás con un 302
  3. El formulario vuelve relleno: old() y @error, una sola vez
  4. POST válido: mensaje flash con with() y 302 al listado
  5. GET: el listado muestra el mensaje con @session, y se borra
Es el POST/Redirect/GET de 4.1, ahora sin escribir nada de sesión a mano. Tras el paso 5, F5 solo repite el GET: no se envía otra vez el formulario. Pasos 2 y 3: lo que en 3.8 hacíamos con ValidadorCurriculo y cada value. La sesión guarda los errores solo hasta la petición siguiente.

old() y $errors


<label for="nombre" class="block font-semibold">Nombre</label>
<input type="text" name="nombre" id="nombre" value="{{ old('nombre') }}"
       @class(['mt-1 w-full rounded border p-2', 'border-red-500' => $errors->has('nombre')])>
@error('nombre')
    <p class="mt-1 text-sm text-red-700">{{ $message }}</p>
@enderror
  • old('nombre', $proyecto['nombre']): en la edición, el valor del proyecto si no hay nada anterior.
  • $errors llega a todas las vistas. Un resumen: $errors->any(), $errors->all().

Form Requests


php artisan make:request ProyectoRequest
        

class ProyectoRequest extends FormRequest
{
    /** ¿Puede hacer esta petición? La autorización, en el Bloque 7. */
    public function authorize(): bool { return true; }

    public function rules(): array
    {
        return ['nombre' => ['required', 'string', 'max:100'], /* ... */];
    }

    public function messages(): array
    {
        return ['nombre.required' => 'El nombre del proyecto es obligatorio.'];
    }

    public function attributes(): array { return ['fecha_fin' => 'fecha de fin']; }
}

En app/Http/Requests/. Lo mismo que ValidadorCurriculo en 3.8.

El Form Request, en la acción


use App\Http\Requests\ProyectoRequest;

public function store(ProyectoRequest $request)
{
    $datos = $request->validated();
    // ...
}
  • Valida antes de que empiece store(): si falla, la acción no se ejecuta.
  • validated(): solo los campos validados.

Mensajes flash

En la sesión, durante una sola petición: la siguiente.


return redirect()->route('proyectos.index')
    ->with('mensaje', "Proyecto «{$datos['nombre']}» creado.");

En el layout, encima de {{ $slot }}:


@session('mensaje')
    <div class="mb-6 rounded border border-green-300 bg-green-50 p-4 text-green-800">
        {{ $value }}
    </div>
@endsession

En 4.1, leer de $_SESSION y unset(). Aquí se borra solo.

¿Dónde se guarda el proyecto?

En ningún sitio, todavía: los proyectos son un array del controlador y cada petición empieza de cero (2.4).

  • store y update validan y redirigen con un mensaje.
  • En el Bloque 6, a la base de datos.
  • ¿Ficheros? enctype="multipart/form-data" y $request->file('foto'). Todo, en el Bloque 7.

Puente

En v0

$_POST campo a campo, una clase validadora, cada value a mano y el mensaje guardado y borrado de la sesión.

En Laravel

El Form Request valida antes de la acción, old() y $errors rellenan el formulario, y with() deja un mensaje que se borra solo.

Esto que hicimos a mano, el framework lo automatiza así.
