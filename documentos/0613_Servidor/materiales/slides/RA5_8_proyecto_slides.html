Un array en el controlador no es un modelo, es un apaño. El modelo de verdad:

  • Las clases del dominio, Ciclo y Curriculo, como en 3.5;
  • un repositorio, que sabe guardarlas y recuperarlas.

MVC completo

  1. GET /mi-curriculo, con auth: llega a MiCurriculoController
  2. El controlador solo conoce la interfaz: delUsuario(7)
  3. El contenedor le dio un JsonCurriculoRepository (singleton), que lee el fichero
  4. Vuelve un objeto del dominio: Curriculo, con su Ciclo
  5. El controlador pasa los datos a la vista y el HTML vuelve al navegador
  6. Bloque 6: otra implementación, una línea en el contenedor; el controlador no cambia
El modelo son dos cosas: las clases del dominio (Curriculo, Ciclo) y el repositorio que las guarda y recupera. Paso 4: el objeto viaja de verdad desde el repositorio hasta el controlador. Paso 6: el mismo hueco de la interfaz admite otra implementación.

Las clases de v0, en app/

  • De vanilla_php/src/ a app/Dominio/, con espacio de nombres y sin require_once (5.2).

El patrón repositorio

Guarda y recupera los objetos de un tipo, como una colección. Quien lo usa no sabe dónde.


interface CurriculoRepository
{
    public function todos(): array;          // list<Curriculo>

    public function delUsuario(int $userId): ?Curriculo;

    public function guardar(Curriculo $curriculo): void;    // alta o sustitución
}

Una interfaz (3.5): qué sabe hacer, sin decir cómo.

Una implementación: un array


final class ArrayCurriculoRepository implements CurriculoRepository
{
    private array $curriculos = [];      // indexados por el id de su usuario

    public function delUsuario(int $userId): ?Curriculo
    {
        return $this->curriculos[$userId] ?? null;
    }

    public function guardar(Curriculo $curriculo): void
    {
        $this->curriculos[$curriculo->userId] = $curriculo;
    }
    // ... todos(): array_values($this->curriculos)
}

Los controladores dependen solo de la interfaz: otra implementación no los toca.

Inyección de dependencias


class CurriculoController extends Controller
{
    public function __construct(
        private readonly CurriculoRepository $curriculos,
    ) {}

    public function index(): View
    {
        return view('curriculos.index', ['curriculos' => $this->curriculos->todos()]);
    }
}

El controlador no lo crea: lo pide, y Laravel se lo entrega. Como el Request de 5.6.

El contenedor de servicios

A una interfaz no se le puede hacer new. En AppServiceProvider::register():


public function register(): void
{
    $this->app->singleton(CurriculoRepository::class, ArrayCurriculoRepository::class);
}

"Cuando alguien pida un CurriculoRepository, entrégale un ArrayCurriculoRepository… y siempre el mismo."

El patrón Singleton

Una clase con una sola instancia, compartida. La forma clásica:


final class Configuracion
{
    private static ?Configuracion $instancia = null;

    private function __construct() {}     // nadie puede hacer new Configuracion()

    public static function instancia(): self
    {
        return self::$instancia ??= new self();
    }
}

Singleton: clásico o del contenedor

ClásicoDel contenedor
La clase obliga a una sola instanciaLa clase es normal; el contenedor la comparte
Quien la usa queda atado a Configuracion::instancia()Quien la usa pide la interfaz
En los tests no se puede sustituirEn los tests, una línea

PHP empieza de cero en cada petición (2.4): "única" durante una petición.

Un repositorio que recuerda

Con el array, el currículo guardado desaparece en la petición siguiente: la lección de 4.4.

  • Sin base de datos hasta el Bloque 6, pero con un sitio que sobrevive y es compartido: un fichero.
  • JsonCurriculoRepository, con las funciones de PHP que ya conocemos.

JsonCurriculoRepository


final class JsonCurriculoRepository implements CurriculoRepository
{
    public function __construct(private readonly string $fichero) {}

    public function guardar(Curriculo $curriculo): void
    {
        $todos = $this->leer();
        $todos[$curriculo->userId] = ['user_id' => $curriculo->userId, 'alumno' => $curriculo->alumno,
            'ciclo' => $curriculo->ciclo->codCiclo, 'video' => $curriculo->videoCurriculum];

        // LOCK_EX: si dos peticiones escriben a la vez, la segunda espera.
        file_put_contents($this->fichero, json_encode($todos, JSON_PRETTY_PRINT), LOCK_EX);
    }

    private function leer(): array
    {
        return is_file($this->fichero)
            ? json_decode(file_get_contents($this->fichero), true) ?? [] : [];
    }
    // ... todos() y delUsuario() convierten los arrays en objetos Curriculo
}
Resumido para que quepa: el código completo, en el .md (con JSON_UNESCAPED_UNICODE y el método aCurriculo()).

El nombre sale de la sesión


public function update(CurriculoRequest $request): RedirectResponse
{
    $datos = $request->validated();

    $this->curriculos->guardar(new Curriculo(
        $request->user()->id,
        $request->user()->name,
        Ciclo::catalogo()[$datos['ciclo']],
        $datos['video'] ?? null,
    ));

    return to_route('mi-curriculo')->with('mensaje', 'Currículo guardado.');
}

Puente

En v0

Cada página hacía new ValidadorCurriculo($ciclos), require_once de sus clases y guardaba en $_SESSION.

En Laravel

Las clases se cargan solas, el contenedor entrega a cada controlador lo que pide y el repositorio esconde dónde se guardan los datos.

Esto que hicimos a mano, el framework lo automatiza así.
